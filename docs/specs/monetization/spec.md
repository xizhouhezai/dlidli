## 1. 背景与商业化原则

- **体验优先**：不做贴片广告；广告仅限信息流原生卡片且有明确"广告"标识。
- **多元收入**：会员订阅（稳定）+ 打赏分成（社区）+ 广告（规模后）。

用户故事：

- 作为 **观众**，我可以购买大会员获得清晰度/专属内容权益，以便更好的观看体验。
- 作为 **观众**，我可以给喜欢的 UP 主充电，以便直接支持创作。
- 作为 **UP 主**，我可以获得充电分成与创作激励，以便持续创作。

### 2.6 支付依赖关系（与直播域的接口）

- 直播礼物域（[live spec](/specs/live/spec) LIV-13 §5D）当前的开发直充 `POST /admin/dev/recharge` 是**临时通道**，其 `RechargeTx` 的 `biz_no` 幂等设计即为本卡支付回调的替换点；PAY-01 交付后该接口下线由 **M4-PAY-02 / 后续卡**执行（本卡不删，只保证支付回调侧的幂等契约与其一致：**同一业务单号重复入账只生效一次**）。
- 本卡**不引入**任何金瓜子/硬币写入路径。

## 3. 边界与异常

- **IF** 支付回调重复到达 **THEN THE SYSTEM SHALL** 以幂等键保证只结算一次。
- **IF** 用户为未成年人 **THEN THE SYSTEM SHALL** 执行消费限制（合规）。
- **IF** 回调签名不合法 **THEN THE SYSTEM SHALL** 拒绝该回调，且订单状态与资金流水**均不得发生变化**（抗伪造，见 §6.3）。
- **IF** 渠道适配器未实现（真实渠道未接入） **THEN THE SYSTEM SHALL** 返回可区分的「渠道未实现」错误，而不是静默失败或伪造成功。

## 6. 支付基础设施细化（PAY-01，V3.0）

> 交付形态：**全量机制 + mock 渠道**（资质现实见 §2.5 说明）。技术决策见 [plan §2E](/specs/monetization/plan)。
> 任务：M4-PAY-01（[tasks](/specs/monetization/tasks)）。

### 6.1 金额与账户分离（硬约束）

- **THE SYSTEM SHALL** 以**整数「分」**存储与计算一切金额：DB 列类型 `BIGINT`，Go 类型 `int64`，JSON 传输亦为整数分。**禁止 `float32`/`float64` 参与任何金额运算或存储**（含临时变量、聚合、比较）。
- **THE SYSTEM SHALL** 提供独立的现金账户体系（`cash_account` 余额 + `cash_log` 流水），与虚拟币账户（`user.coin`/`coin_log` 硬币、`melon_seed_account`/`melon_seed_log` 金瓜子）**严格分离**：
  - 支付订单的入账/退款**只写现金账户**，**SHALL NOT** 写 `coin_log`、`melon_seed_account`、`melon_seed_log` 任何一张表。
  - 现金 → 虚拟币的兑换关系**不在本卡**（属 M4-PAY-02 / 会员卡），本卡不提供任何兑换接口。

### 6.2 订单系统与状态机

- **WHEN** 用户下单 **THE SYSTEM SHALL** 创建订单：订单号（对外业务单号，全局唯一）、用户、金额（分）、渠道、商品描述、状态 `待支付(0)`、过期时间（`下单时间 + 配置的超时分钟数`）。
- **THE SYSTEM SHALL** 维护状态机：

  | 状态 | 值 | 允许的迁移 |
  | --- | :-: | --- |
  | 待支付 | 0 | → 已支付(1) / 已关闭(2) |
  | 已支付 | 1 | → 已退款(3) |
  | 已关闭 | 2 | 终态 |
  | 已退款 | 3 | 终态 |

- **THE SYSTEM SHALL** 以**条件 UPDATE**（`WHERE status = <期望值>`）执行每一次状态迁移，并**以受影响行数判定是否真正发生迁移**：受影响行数为 0 即表示并发/重放对手已先行完成迁移，调用方**SHALL NOT**重复执行副作用（入账/退款）。
- **WHEN** 订单处于待支付 **AND** 已过过期时间 **THE SYSTEM SHALL** 由关单机制将其置为已关闭；**IF** 已关闭订单再收到支付成功回调 **THEN THE SYSTEM SHALL** 拒绝该回调（错误码可区分），**SHALL NOT** 把订单改回已支付。
- **IF** 已支付订单再收到支付成功回调 **THEN THE SYSTEM SHALL** 按幂等处理（返回订单当前状态，不重复入账、不报错）。
- **WHEN** 用户对已支付订单发起退款 **AND** 金额合法 **THE SYSTEM SHALL** 经渠道适配器退款成功后，将订单置为已退款并写现金账户退款流水（负向）；**IF** 订单非已支付态 **THEN** 拒绝（可区分错误码）。

### 6.3 支付网关（适配器模式 + mock 渠道）

- **THE SYSTEM SHALL** 定义统一渠道适配器契约，包含四个方法：**下单 / 查单 / 退款 / 回调验签**。业务侧（订单服务）只依赖该接口，不依赖任何具体渠道。
- **THE SYSTEM SHALL** 提供 **mock 渠道**（`channel=mock`）实现，用于全链路联调与验收，**支持模拟支付成功/失败/超时/重复回调**。
- **THE SYSTEM SHALL** 为支付宝与微信支付提供**适配器骨架**（换入点）：类型、名称、接口实现签名齐备；未接入真实凭据时，**IF** 调用其下单/查单/退款 **THEN THE SYSTEM SHALL** 返回「渠道未实现」可区分错误，**SHALL NOT** 返回伪造的成功。
- 骨架代码 **SHALL** 以注释写明接入步骤（凭据配置、签名算法、回调地址备案、对账文件下载与解析），使后续接入无需改动业务侧与表结构。
- **WHERE** 渠道不存在或未启用 **THE SYSTEM SHALL** 在下单时拒绝（可区分错误码）。

### 6.4 回调：验签 + 幂等（抗伪造）

- **THE SYSTEM SHALL** 提供 `POST /pay/callback/{channel}` 回调端点（**无用户鉴权**——回调来自渠道服务器，鉴权靠签名）。
- **WHEN** 收到回调 **THE SYSTEM SHALL** 先调用该渠道的**回调验签**方法；**IF** 验签失败 **THEN THE SYSTEM SHALL** 拒绝（可区分错误码）、记录一条验签失败的回调日志，且**订单状态与现金流水均不发生任何变化**。
- **THE SYSTEM SHALL** 以 **`渠道 + 渠道交易号` 作为幂等键**（DB 唯一索引承载）：同一渠道交易号的支付结果**只生效一次**。
- **WHEN** 同一回调被重放 N 次 **THE SYSTEM SHALL** 保证订单状态只迁移一次、现金流水**只有一份**（幂等键与条件 UPDATE 双重保证）。
- **WHEN** 同一订单被并发回调 **THE SYSTEM SHALL** 保证**恰好一次**入账（事务 + 条件 UPDATE 行锁串行化）。
- **THE SYSTEM SHALL** 记录每一次回调的原始报文与验签结果（审计与重放取证），供对账与人工排查使用。

### 6.5 对账（本地一致性核对 + 异常清单）

- **WHEN** 对账任务运行（按日期） **THE SYSTEM SHALL** 按「渠道 × 日期」聚合生成日对账单：订单数、已支付单数、已支付金额、退款单数、退款金额、本地流水合计、差异数、异常状态标记。
- **THE SYSTEM SHALL** 生成异常订单清单，至少覆盖以下类型：**金额不符**（回调记录的金额 ≠ 订单金额）、**长期挂起**（订单超时后仍长期停留在待支付）、**流水缺失**（订单已支付但无对应现金流水）、**重复回调**（同一订单收到的成功回调次数 > 1；**渠道重复投递是常态**，故本项登记的是「重复投递发生」这一事实供人工确认幂等是否生效——若同时该订单的现金流水 > 1 条，才是幂等被击穿）。
- **THE SYSTEM SHALL** 提供异常订单的人工处理能力（查询 / 处理 / 处理备注 / 处理人与时间）。
- **边界（不在本卡）**：**真实渠道对账文件（支付宝/微信账单下载与解析）是显式换入点**，本卡的「本地一致性核对」不依赖渠道文件。对账**不含自动冲正**（plan 决策：自动冲正风险高，差异走人工处理台）。

### 6.6 合规钩子（接口留设，实现程度写明）

- **THE SYSTEM SHALL** 在「下单」与「回调入账」两个位置留设**消费限制钩子**接口，默认实现放行，真实规则为显式替换点。
- **THE SYSTEM SHALL** 留设**退款通道**（退款走渠道适配器的退款方法），保证合规退款有可执行路径。
- **实现程度与未覆盖边界（必须如实声明）**：本项目 `user_auth` 当前**没有出生日期/年龄字段**，实名判定仅为「存在手机/邮箱记录」（[account spec](/specs/account/spec) ACC-23 能力位未落地到年龄维度）。因此本卡**只交付钩子接口与调用点**，**未成年人识别的数据基础不具备**，真实限制规则待 ACC-23 补全后接入——该事实登记为未覆盖项。
- **THE SYSTEM SHALL NOT** 以「已实现未成年人限制」宣称合规达标；资质与规则落地属运营/合规线程。

### 6.7 管理端（挂后台鉴权链）

- **THE SYSTEM SHALL** 提供管理端能力：订单查询、异常订单处理台、手动补单（人工确认收款并入账）。
- **THE SYSTEM SHALL** 将上述接口挂 `AdminAuth` + 权限点（写法对齐既有 `POST /admin/dev/recharge`），且**权限点须落库**（非仅路由存在）。
- **IF** 请求未携带管理员令牌或令牌无效 **THEN** 401；**IF** 令牌有效但缺少权限点 **THEN** 403。
- **THE SYSTEM SHALL** 保留一个 `POST /admin/dev/pay-callback`（挂 admin 权限）用于模拟渠道回调联调，与真实渠道回调**走同一条处理链**（不得是旁路实现）。

### 6.8 错误码

- 沿用 9xxxx 商业化段。直播子段已用 91001-91030，**支付子段自 92001 起**（92001-92012，见 plan §2E.9）。
