## 0. 怎么用这份手册

**执行者假设**：只有本机（`D:\studyspace\dlidli`）+ 一部 API 26 的真机。不需要读 spec/plan/tasks 全文，不需要额外上下文；本手册自包含。

**三条硬口径**（违反即结论无效）：

1. **模拟器结论不作数**。模拟器是 **x86_64 软件渲染**（`SP_daemon -deviceinfo` 报 `hmos.emulator` / `abilist x86_64`，走宿主 Intel Arc 转译，`GL_RENDERER` 报 `Mali-G77` 只是字符串），且无功耗采集能力（`SP_daemon -p` 报 `RK does not support power acquisition`，电池是虚拟的 100%/充电中）。凡本手册 §1 表内「模拟器为何验不了」一栏非空的项目，**真机数值必须重测，禁止用模拟器值填空**。
2. **判定标准以 spec 为准**。凡 spec 未定义的阈值，本手册统一写「**待定，需与产品确认**」，不自行编数。执行时若该条仍无阈值，记录实测值 + 判定列填「待定（无阈值）」，不要硬判 PASS/FAIL。
3. **标记来源**。每项标注 **「模拟器已验，真机需复核」** 或 **「模拟器完全无法验」**——前者只复核绝对数值/设备行为，不必重复走功能流程；后者必须从零执行。

**产物落点**：证据放 `.dev-logs/harmony-device-manual/evidence/<AC-编号>/`，命名见 §5。验收完成后把 §4 汇总表填满即可交付。

## 2. 环境准备（开工前一次做完）

### 2.1 真机连接

```powershell
# 本机 hdc（不在 PATH 上，用绝对路径；版本 3.2.0f）
$hdc = "D:\Program Files\Huawei\DevEco Studio\sdk\default\openharmony\toolchains\hdc.exe"

# USB 连接：手机开启「开发者模式 → USB 调试」，数据线插入后
& $hdc list targets -v          # 期望：出现设备 key（一串序列号/TCP 地址），状态 Online
```

- **首次连接**：手机上会弹「允许调试」，必须点允许；未授权时 `list targets` 为空或 `Offline`。
- **无线连接**（USB 不方便时）：`& $hdc tconn <手机IP>:<port>`（同一网段；port 需在手机上开启无线调试后取得）。
- **后续所有命令加设备前缀**：`& $hdc -t <key> shell "..."`。真机下 `<key>` 是 `list targets` 打出的那串；**模拟器是 `127.0.0.1:5555`**，两者不能混用。
- 设备未就绪时的报错是 `[E001005] Device not found or connected`——先回到 `list targets` 确认，不要在这个状态下反复 install。

**记录**：机型 / 系统版本 / API 版本 / hdc key，填进 §4 汇总表表头。

```powershell
& $hdc -t <key> shell "param get const.ohos.apiversion; param get const.product.model; param get const.product.software.version"
```

### 2.2 构建与安装

> ⚠️ **必须用 DevEco 自带的 node**。系统 PATH 上的 node **若为 16.x**，会在 hvigor 启动阶段报 `TransformStream is not defined` 直接失败（本仓既往环境事实）。
> 本机实测：DevEco 自带 **v24.14.1**（`D:\Program Files\Huawei\DevEco Studio\tools\node\node.exe`）；系统 PATH 上当前是 **v22.20.0**（不是 16.x，故本机未复现该报错）。另需 `DEVECO_SDK_HOME` 指向 SDK 根（本机默认**未设置**，必须显式设）。
> 稳妥做法是照下面这样把 DevEco 的 node 前置到 PATH——这条命令本身就是防 16.x 的那道闸。

```powershell
$env:DEVECO_SDK_HOME = "D:\Program Files\Huawei\sdk"
$env:PATH = "D:\Program Files\Huawei\DevEco Studio\tools\node;" + $env:PATH
Set-Location D:\studyspace\dlidli\apps\harmony

& "D:\Program Files\Huawei\DevEco Studio\tools\hvigor\bin\hvigorw.bat" --no-daemon assembleHap
# 期望：BUILD SUCCESSFUL；产物
#   apps\harmony\entry\build\default\outputs\default\entry-default-unsigned.hap
```

**真机安装的关键差异（必读）**：当前 `apps/harmony/build-profile.json5` 的 `signingConfigs` 为 **空数组**——**未签名 HAP 只能装进模拟器**（模拟器实测 `hdc install` 成功）。真机安装前必须先配签名：

1. DevEco Studio → `File` → `Project Structure` → `Project` → `Signing Configs`；
2. 勾选 `Automatically generate signature`（需登录华为开发者账号），DevEco 会写入 `signingConfigs` 并产出 **signed** HAP；
3. 重新构建，产物路径同上但文件名不含 `-unsigned`。

```powershell
# 安装（<hap> 用相对路径：先 cd 到产物目录；Git Bash 下传 Windows 绝对路径会被拼成 <当前目录>/D:/... 而报 Error opening file）
Set-Location D:\studyspace\dlidli\apps\harmony\entry\build\default\outputs\default
& $hdc -t <key> install -r entry-default-signed.hap

# 启动
& $hdc -t <key> shell "aa start -a EntryAbility -b com.dlidli.app -m entry"
# 若报 10104001：多半不是包名问题，而是安装失败（同上）或 DevEco 缓存里的旧包名
```

### 2.3 后端地址（真机 ≠ 模拟器）

模拟器用 `http://10.0.2.2:8000`（QEMU 用户态网络直连宿主 loopback）。**真机没有这个映射**——手机与宿主必须在同一局域网，把 `ApiConfig.BASE_URL` 改成宿主的**局域网 IP**：

```powershell
# 查宿主局域网 IP
Get-NetIPAddress -AddressFamily IPv4 | Where-Object { $_.IPAddress -notlike '127.*' } | Select-Object IPAddress,InterfaceAlias
# 验证手机能到（在手机浏览器打开 http://<宿主IP>:8000 应能通；或从设备 shell 里 curl）
& $hdc -t <key> shell "curl -s -o /dev/null -w '%{http_code}' http://<宿主IP>:8000/api/v1/categories"
```

⚠️ 该地址由 `common/constants/ApiConfig.ets` **单点维护**（tasks M4-HMY-03 已登记）。若验收不想改代码，可用端口反向转发把设备侧 `127.0.0.1:8000` 指到宿主：

```powershell
& $hdc -t <key> rport tcp:8000 tcp:8000   # 设备 127.0.0.1:8000 -> 宿主 8000
& $hdc -t <key> fport ls                  # 查看已建立的转发；撤掉用 fport rm <taskstr>
```

### 2.5 性能数据获取

**① 帧率（唯一在本仓库验证过有效的方法）**——数应用进程的 vsync 标记：

```sh
PID=$(pidof com.dlidli.app)
hitrace -t 10 -b 65536 -o /data/local/tmp/perf.ftrace graphic ace animation
# 宿主机侧统计（帧率 = (条数-1) ÷ 首末 now 纳秒差）
grep "B|$PID|H:OnVsyncEvent" /data/local/tmp/perf.ftrace | sed -n 's/.*now:\([0-9]*\).*/\1/p' > frames.txt
```

- **两条铁律**（M4-HMY-01 踩过）：① **不能用「固定窗口数帧数」**——静止时该标记为 **0**（系统按需出帧）；② `hidumper -s RenderService -a fpsCount` 与 `SP_daemon -f` / `-ohtestfps` 在**模拟器上恒为空/固定值**（前者 60/1，后者 fps=0）。真机上这三条是否可用**未验**，建议以 hitrace 为准、其余仅作交叉印证。
- 交叉印证（同一 trace 内数 RenderService 侧）：`RSUniRenderThread::Render`（出图次数）、`RSSurfaceRenderNodeDrawable::OnDraw`、**`wouldDrawLargeAreaBlur`**（大面积模糊＝材质开销）、`RSFilterCacheManager::ClearFilterCache`。

**② 冷启动 / 起播**：按 hilog **时间戳做差**（脚本见 `.dev-logs/m4hmy10/measure-coldstart.ps1`、`measure-playstart.ps1`，把其中的 `$dev` 从 `127.0.0.1:5555` 改成真机 key 即可直接跑）。

**③ 功耗**：`SP_daemon -p`（模拟器报不支持，**真机可用性是本手册 AC-06 的未知项之一**，需现场试）；备选取 DevEco Studio **Profiler** 的 Energy 面板；再备选系统「设置 → 电池 → 耗电排行」。

**④ 内存**：`hidumper --mem <pid>`（取 PSS/RSS），或 Profiler 的 Memory 面板。

& $hdc -t <key> shell "snapshot_display -f /data/local/tmp/ac01.jpeg"
& $hdc -t <key> file recv /data/local/tmp/ac01.jpeg D:\studyspace\dlidli\.dev-logs\harmony-device-manual\evidence\AC-01\ac01.jpeg

## 3. 分组验收

### G1 · 性能与帧率（AC-01 / AC-02 / AC-03 / AC-04 / AC-05）

> **这组为什么必须真机**：模拟器是 x86_64 软件渲染 + 宿主转译，**没有硬件解码直通**，播放类耗时与帧率完全不可外推；而 spec §4 的三条硬阈值（<2s / P90<1.5s / ≥55fps）恰恰都是**真机口径**写进 spec 的。另有一层：模拟器在 60Hz vsync 上限下**还有余量**，能把真实开销（材质模糊绘制次数 1.41×~3.15×）整个吸收掉——这正是「模拟器不掉帧」不能等于「真机不掉帧」的机制解释。

#### AC-01 冷启动耗时

**观测对象**：`Ability onCreate`（系统域）→ 首页日志 `信息流加载完成`（应用域）的毫秒差。

**前置**：真机已连；应用已登录（避免登录态竞态干扰）；后端可用；手机**不要插着 USB 调试线反复传文件**（干扰 I/O）。

**步骤**
1. `& $hdc -t <key> shell "aa force-stop com.dlidli.app"`，等 1.5s。
2. `& $hdc -t <key> shell "hilog -r"`，等 300ms。
3. 记录宿主时间，`aa start -a EntryAbility -b com.dlidli.app -m entry`。
4. 等 10s，抓 `hilog -x -D 0x0,0xD11D`，落盘。
5. **重复 6 轮**（≥6 次才有分位数意义）。
6. 每轮从日志里取两个时间戳做差。

**观测点**：hilog 行首的 `MM-dd HH:mm:ss.fff`；两域合并抓取才能同时拿到 `onCreate` 与 `信息流加载完成`。

**记录表**

| 1 | | | | coldstart-run1.log |
| … | | | | |
| 6 | | | | |

#### AC-02 播放起播时间（P90）

**观测对象**：`VideoPlayer` 的 `状态：initialized` → `状态：playing`，同时拆分 `init→prepared` 与 `prepared→playing`。

**前置**：已在搜索结果页/首页，目标卡片可见；应用域日志级别为 DEBUG；网络为 Wi-Fi。

**步骤**
1. `uitest uiInput keyEvent Back` 回到列表，等 1.5s。
2. `hilog -r` 清空，等 300ms。
3. `uitest uiInput click <卡片X> <卡片Y>` 进播放页。
4. 等 25s，抓 `hilog -x -D 0xD11D`，落盘。
5. **重复 10 轮**（同一稿件、同一清晰度，排除「首开编解码冷启」）。
6. 额外单独跑 1 次**冷启首开**（杀进程后首次进播放页），单独记录、**不计入 P90**。

**观测点**：日志里 `VideoPlayer: … (idle|initialized|prepared|playing|…) … reason=` 这几条状态行的秒级时间戳。控件坐标用 `uitest dumpLayout -p /data/local/tmp/layout.json` + `hdc file recv` 现取（**不要照抄模拟器坐标**，分辨率不同）。

**记录表**

| 轮次 | init→prepared(ms) | prepared→playing(ms) | 合计(ms) | 证据 |
| --- | --- | --- | --- | --- |
| 1..10 | | | | playstart-runN.log |

**P90 算法（必须写死，否则同一批数据会算出两个数）**：最近秩法——按升序排，取**第 `ceil(0.9 × N)` 位**。N=10 时即第 9 位。
> 口径自证：以上述算法算模拟器那 10 轮（3113/3378/3460/3501/3593/3614/3740/3805/**3837**/4036），P90 = **3837ms**——与 spec §4 记载的 3837ms 一致；若改用「floor 索引」会错算成 4036ms。

**判定标准**：10 轮合计的 **P90 < 1500ms** 为 PASS（来源：spec §4 第 2 行目标列 `P90 < 1.5s`）。

> **本节解析逻辑已离线跑通（2026-10-20，非真机）**：用上述正则对 10 份真实 `playstart-runN.log` 逐字执行，得 3113~4036ms、**均值 3608ms / P90 3837ms**，与 spec §4 记载一致，证明状态机正则与 P90 算法可用。
⚠️ **模拟器 3837ms 的 P90 不得作为对比基线**——spec §4 明写该数值「不得外推为真机结论、更不得据此判定鸿蒙不支持」。若真机 P90 仍 >1.5s，先查 AC-13（网络）与 AC-04（换源），再判 FAIL。
⚠️ 起播超时阈值 `STATE_TIMEOUT_MS` 现为 **30s**（模拟器冷启曾需 15.0~15.5s 才到 prepared，原 15s 阈值会误判失败）。真机若出现「起播超时，请重试」而日志显示 prepared 在 30s 后才到，记录该时间并回报——不要自行改代码。

#### AC-03 弹幕满载渲染帧率

**观测对象**：播放页在**同屏数十条弹幕**下的出帧率。

**前置**：**≥60fps 片源**（必须！示例片源 30fps 会把整页锁在 30fps，永远测不出 55fps）；弹幕开关为「开」；段缓存预热好（先播一遍让弹幕拉全）。造满载：给该稿件灌入几十条同时刻弹幕（走正常发送接口，或后端段缓存预置）。

**观测点**：① hitrace 帧率与 p90；② 同屏弹幕条数截图；③ 交叉印证 `wouldDrawLargeAreaBlur`（材质叠加对帧率的贡献）。

| 1..3 | 满载·弹幕开 | | | | | ac03-rN.ftrace |
| 1..3 | 满载·弹幕关 | | | | | ac03-off-rN.ftrace |

**判定标准**：满载·弹幕开时 **均值 ≥ 55fps** 为 PASS（来源：spec §4 第 3 行目标列 `≥ 55fps`；spec §4 备注进一步要求「满载 + ≥60fps 片源 + 真机」三者同时满足，缺一即不作达标证据）。

### G2 · 功耗与发热（AC-06）

> **这组为什么必须真机**：模拟器**没有功耗采集能力**——`SP_daemon -p` 直接报 `RK does not support power acquisition`，电池是虚拟常量（100% / 充电中）。功耗与发热是**电池 + SoC + 散热结构**共同决定的物理量，模拟器上连可测量的对象都不存在，不存在任何「近似外推」的空间。

### G3 · 渲染与观感（AC-07 / AC-08 / AC-09）

> **这组为什么必须真机**：三者的共同点是「**模拟器把差异藏起来了**」。材质：模拟器在 60Hz 上限下有富余算力，模糊路径绘制次数翻 1.4~3.2 倍也测不出帧率差；暗色模式：模拟器 `param set persist.sys.color.mode` 报 **errNum 1001**、`settings` 二进制缺失，**根本切不过去**；黑边：本机内容全是 16:9，稳态下 `bar=0` 分支**不可达**。三条都属于「不是测得不准，而是测不到」。

### G4 · 保活与后台（AC-10 / AC-11 / AC-12）

> **这组为什么必须真机**：保活与吞吐**不是应用自己的性质，是设备与系统策略的性质**。省电策略、厂商后台管控、`backgroundModes` 是否真的被授予、Wi-Fi 与蜂窝的实际路径与速率，模拟器一个都不具备——而且模拟器上 `moveAbilityToBackground()` 可能直接返回 `16000065`（该 API 仅前台可调），连「切后台」这个动作本身都不可靠。同尺寸对照中还出现过切后台即被 WMS 回收进程的情形，**「系统任务解耦」的观察不能当作保活证据**。

#### AC-10 后台长时任务保活（锁屏 + 切后台 5 分钟）

**观测对象**：上传进行中，锁屏并切后台，5 分钟后任务是否仍在推进并最终收口。

**前置**：一份 30MB 视频；后端可用；`backgroundModes: ["dataTransfer"]` 与 `KEEP_BACKGROUND_RUNNING` 已声明（已在代码里）；**真机省电策略为默认值**（不要先手动加白名单，那会掩盖问题）。

**步骤**
1. 进「我的 → 投稿」，选 30MB 片，开始上传；记录起始时刻 t0。
2. 立即按电源键**锁屏**（`& $hdc -t <key> shell "power-shell suspend"` 或手动按电源键）。
3. 再切后台（上滑回桌面），保持 **5 分钟**。期间不做任何操作。
4. 5 分钟后解锁、回前台，看界面阶段。
5. 收口后**由宿主机对后端落盘的合并成品重算 SHA-256**，与端侧上报的 `file_hash` 逐字节比对——**判定不读端侧自述**。

6. 跑 3 次（真机后台策略有时间窗与厂商差异，一次不算数）。

**观测点**：界面阶段文案（正在校验文件 → 正在上传 → 正在合并文件 → 上传完成）；日志 `上传` / `complete` / `file_id`；后端 `server/uploads/chunks/<uploadId>/<index>.part` 的落盘进度；**成品 sha256 与文件名的比对结果**（硬判据）。

### G5 · 弱网与稳定性（AC-13 / AC-14 / AC-15）

> **这组为什么必须真机**：弱网需要**可复现的丢包/抖动/RTT**，模拟器的 QEMU 用户态网络不可控（它只提供 `10.0.2.2` 直连宿主 loopback 这条路，连「网络变慢」都造不出来）；崩溃率与内存增长则是**长时运行 + 真实系统态**下的性质，模拟器的秒级采样窗口和虚拟内存镜像都给不出代表性样本。

#### AC-13 弱网与重试

**观测对象**：四种弱网下的行为——限速、高丢包、断网再恢复、以及「上传中断后续传」。

**前置**：能控制网络的中间设备（路由器 QoS、或宿主用 `clumsy`/`netem` 之类在共享网段上做整形）；真机与宿主同网段。

**步骤**
1. **限速 ≥500ms RTT**：进播放页，观察起播耗时、是否触发 `STATE_TIMEOUT_MS`（30s）失败态、失败文案是否正确（应为「起播超时，请重试」而非「播放失败（undefined）」）。
2. **高丢包 20%**：滚动首页，观察 `HttpClient` 退避重试（仅网络类与 5xx 可重试，300ms×2ⁿ 共 3 次）是否按预期发生、最终是否出错误态而非白屏。
3. **断网再恢复**：播放中拔网 10s 再恢复，验证 spec §3「保留进度并可从断点续播」。
4. **上传中断续传**：上传到中途中止（杀网），恢复后重进投稿页，看是否只补缺失分片、不重传已传分片。

**观测点**：日志里 `status=… code=…` 与重试次数；`ErrorStateView` 是否出现且可重试；续传时 `uploaded=[…]` 与 `resumed=true`；实际发送的分片数。

**记录表**

| 场景 | 现象 | 是否通过 | 证据 |
| --- | --- | --- | --- |
| 限速 ≥500ms RTT 起播 | | | |
| 高丢包首页重试 | | | |
| 断网恢复续播 | | | |
| 上传中断续传 | | | |

**判定标准**：**数值阈值：待定，需与产品确认**（spec 无弱网阈值）。
可判定的部分（引 [spec §3](/specs/harmony/spec)）：① 播放中网络中断 → **保留进度**且恢复后可续播；② 失败态必须可重试、不得白屏、不得出现 `undefined` 文案；③ 续传**只补缺失分片**（`uploaded` 数组外的片不重传）。

#### AC-15 长时播放（>5min）稳定性与内存增长

### G6 · 交互与兼容（AC-16 / AC-17）

> **这组为什么必须真机**：一个**能力缺口**和一个**环境缺口**。相册选图的「选中→裁切」段在模拟器上**根本走不到**——模拟器图库为空（`所有图片` 无内容、`拍照` 无相机应用），只能验到「选择器可打开、取消不脏状态」；核心链路虽然功能已在模拟器验过，但每条的 `未覆盖` 都以「全部结论均在 API 26 模拟器取得，真机待验」收尾，真机上要复核的是**设备相关分支**（硬解、保活、权限、系统面板、IME 行为），不是重复点一遍。

## 5. 发现问题怎么办（缺陷记录格式）

一条问题一个 `defect-<AC编号>-<序号>.md`，落在 `.dev-logs/harmony-device-manual/evidence/<AC-编号>/`。

```markdown
# defect-AC10-01：<一句话现象>

- **关联验收项**：AC-10 后台长时任务保活
- **严重级别**：S1 阻断 / S2 严重 / S3 一般 / S4 轻微（判级见下）
- **真机环境**：<机型> / API <版本> / 系统 <版本>
- **构建产物**：<hap 名> + sha256
- **发生时间**：<yyyy-mm-dd HH:mm:ss>（与 hilog 时间戳对得上）

## 复现步骤
1. …
2. …
3. …
（必须能由第三人照做复现；写清楚点了哪个按钮、在哪一屏、等了多久）

- 预期：（引 spec 条目号 + 原文，例如 spec §2 HMY-50 ①「WHEN 应用切至后台或上传中锁屏 THE SYSTEM SHALL 继续上传」）
- 实际：

## 证据
- 日志：evidence/AC-10/ac10-r1.log（附相关行的**行号与原文**，不要贴整份）
- 截图：evidence/AC-10/ac10-r1.jpeg
- 录屏（可选）：
- faultlogger 条目（崩溃/ANR 必附）：/data/log/faultlog/faultlogger/…（原文）

- 怀疑模块 / 文件：
- 是否与模拟器结论冲突：（是 → 说明这是**设备相关缺陷**，必须真机修；否 → 说明是共性问题，模拟器漏测）

## 处置建议
- 修复 / 记录待排期 / 需产品确认阈值
```

**严重级别判级**（沿用本仓缺陷口径）：

| 级别 | 含义 | 举例 |
| --- | --- | --- |
| **S1 阻断** | 核心链路不可用，或数据损坏 | 上传成品 hash 不 MATCH、审核中稿件数据写坏、登录不可用 |
| **S2 严重** | 主要功能受损但有绕行路径 | 后台保活失败（可前台传完）、弱网下白屏 |
| **S3 一般** | 体验受损、不影响主链路 | 换源画面空白偏长、暗色模式个别文案对比度低 |
| **S4 轻微** | 观感/文案 | 裁切预览尺寸文案措辞、状态胶囊配色 |

**三条纪律**：

1. **发现明显笔误也不要顺手改业务代码**——本卡范围只有文档。登记进缺陷表，单独开卡处理。
2. **不得用模拟器值补真机空缺**：某条真机没测到就在汇总表写「未测」+ 原因，**不要填模拟器数值充数**。
3. **数值型结论必须能追溯到 spec 节号**：汇总表「备注」列写不出来源的数值，说明这个数值不该出现在判定里。
