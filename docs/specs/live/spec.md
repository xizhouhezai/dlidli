## 1. 背景与用户故事

直播提升用户时长与商业化空间（礼物打赏），并为 UP 主提供第二收入曲线。

- 作为 **主播**，我可以通过 OBS 推流开播并管理房间，以便与粉丝实时互动。
- 作为 **观众**，我可以观看直播、发弹幕、送礼物，以便参与实时互动并支持主播。

## 3. 边界与异常

- **IF** 直播内容违规 **THEN THE SYSTEM SHALL** 经截帧机审（每 10s）+ 人工巡查快速切断（M4-LIV-05；细化见 §5E）。
- **IF** 主播对已开播房间重复申请开播 **THEN THE SYSTEM SHALL** 返回「房间已开播」而非重复创建会话。
- **IF** 房间 30 秒内未收到观众心跳 **THEN THE SYSTEM SHALL** 将该观众从在线人数中剔除（见 §5B）。
- **IF** 被禁言观众尝试发言 **THEN THE SYSTEM SHALL** 在弹幕通道拒绝（执行在 LIV-03；禁言记录与到期由本模块 §5C 提供）。

## 4. 合规前置（硬约束）

- 网络文化经营许可证 / 直播相关资质。
- 主播实名 + 未成年人打赏限制与退款通道。
- 直播内容存档 ≥ 60 天（监管要求）。**本卡落地口径**：截帧图 + 机审/巡查判定记录入库留存（`live_frame_audit` / `live_violation_log`），保留期由配置声明（默认 ≥60 天）；**直播回放视频存档**属 LIV-14（下播转码生成回放），不在本卡范围；**推流全量录制**不在第一期（见 §5E.5 替换点）。

## 5A. 房间域细化（LIV-02，V3.1）

### 5A.1 房间生命周期状态机

房间状态 `status`：`0=空闲 idle`（有资格未开播）、`1=直播中 live`、`2=已下播 ended`（本场结束；下一场开播回到 1）。

- **WHEN** 通过开播资格的用户首次申请开播 **THE SYSTEM SHALL** 创建房间（status=0）并生成推流密钥，一主播至多一间。
- **WHEN** 主播调用开播 **AND** 房间 status ∈ {0, 2} **THE SYSTEM SHALL** 开启新场次：status→1、写 `started_at`、清空上场 `ended_at`、在线人数清零重建。
- **IF** 主播在 status=1 时再次调用开播 **THEN THE SYSTEM SHALL** 返回「房间已开播」，不改状态、不换密钥。
- **WHEN** 主播调用下播 **AND** 房间 status=1 **THE SYSTEM SHALL** 结束本场：status→2、写 `ended_at`、在线人数清零。
- **IF** 房间 status ∈ {0, 2} 时调用下播 **THEN THE SYSTEM SHALL** 返回「房间未在直播」。
- **WHEN** 主播修改标题/封面/分区 **THE SYSTEM SHALL** 允许在任意状态修改（开播中改标题即时生效于房间信息查询）。
- **WHILE** 房间 status=1 **THE SYSTEM SHALL** 在列表/详情接口仅返回 status=1 的房间供观众侧消费（status 0/2 不进公开列表）。

### 5A.2 字段约束

| 字段 | 约束 |
| --- | --- |
| 标题 `title` | 必填，1–80 字符（UTF-8 按字符计），开播与更新均校验 |
| 封面 `cover` | 可空字符串（本卡不做封面上传，前端复用 upload 模块后把 URL 存入；≤ 512 字符 URL） |
| 分区 `category_id` | 必填，必须存在于视频分区表（复用 `category`），本卡校验存在性 |
| 推流密钥 | 生成 32 位随机串（crypto/rand），**仅创建时明文返回一次**，库中仅存 bcrypt 哈希；支持「重置密钥」（旧密钥立即失效） |
| 推流地址 | `rtmp://<推流域名>/<room_key>/` 形式占位拼装（域名走配置，本卡不发流、不校验连通性，LIV-01 接 SRS） |

### 5A.3 开播资格（LIV-01 校验逻辑部分）

- 白名单：`live_whitelist`（user_id 唯一，备注/操作人/时间）；资格判定以白名单为第一道闸。
- 实名：依赖账号域实名标记（ACC-23 能力位），本卡按「存在实名标记即通过」实现，接不接真实实名单不阻塞。
- 粉丝数：`relation` 表 `COUNT(*) WHERE target_id = uid` ≥ 100。

### 5B. 在线人数口径（心跳判定）

- **WHEN** 观众进入房间（status=1）**THE SYSTEM SHALL** 记录进房并在在线计数 +1（Redis，键 `live:room:{roomID}:online`）。
- **WHILE** 观众停留在房间 **THE SYSTEM SHALL** 以 ≤ 15s 间隔上报心跳；每次心跳刷新该观众的在线过期标记（TTL 30s，键 `live:room:{roomID}:hb:{uid}`）。
- **IF** 房间 30s 内未收到某观众心跳 **THEN THE SYSTEM SHALL** 该观众视为离线：由「先到期的懒剔除 + 定期对账」从计数扣除（见 plan §2.4 技术决策）。
- **WHEN** 观众显式离开（离房接口）**THE SYSTEM SHALL** 立即计数 −1。
- **口径**：对外展示的「人气值」= 在线人数（本卡不叠加热度系数；系数属 LIV-11 展示侧）。主播本人计入在线人数。同一 uid 同房间重复进房不重复计数（以心跳键存在性判重）。

### 5C. 权限矩阵与房管/禁言（LIV-04 数据与接口部分）

| 操作 | 主播 | 房管 | 观众 |
| --- | :-: | :-: | :-: |
| 开播/下播/改房间信息/重置推流密钥 | ✅ | ❌ | ❌ |
| 任命/撤销房管 | ✅（房管人选自关注粉丝等普通用户，主播不可任命自己） | ❌ | ❌ |
| 禁言用户（时长 1min–720h） | ✅ | ✅ | ❌ |
| 解除禁言 | ✅ | ✅（不可解主播/其他房管，本卡先按「可解非主播」实现） | ❌ |
| 进入房间/上报心跳 | ✅ | ✅ | ✅ |

- 禁言数据模型：`live_room_mute`（房间维度，uid+room 唯一，到期时间；未到期重复禁言覆盖刷新到期）。
- 禁言的**执行**（弹幕通道拦截）属 M4-LIV-03；本卡提供 `IsMuted(roomID, uid)` 判定接口供其调用。
- 房管数据模型：`live_room_admin`（room+uid 唯一）；主播身份由房间表 `anchor_id` 判定，不落房管表。

## 5D. 礼物域细化（LIV-13，V3.2）

### 5D.1 金瓜子资产（与硬币严格分离）

- 资产模型：`melon_seed_account`（user_id 唯一，余额）+ `melon_seed_log`（流水：delta/balance_after/biz_type/biz_no）。**monetization spec 硬约束**：金瓜子与硬币（`user.coin`/`coin_log`）互不转换、互不混淆。
- **强一致（spec LIV-13 原文要求）**：扣款/入账在 MySQL 事务 + `SELECT ... FOR UPDATE` 行锁内完成（余额 → 流水 → 礼物流水 → 分成流水同事务），余额不可为负；并发赠送实测无负余额、无丢单。
- **充值替换点（PAY-01）**：充值入账统一走 `RechargeTx`，`melon_seed_log.uk_biz_no` 唯一键承载幂等——PAY-01 支付回调以支付单号为 biz_no 防重放；**PAY-01 启动前的开发直充走 `POST /admin/dev/recharge`（挂 AdminAuth + RequirePerm，开发期临时通道，届时下线）**。
- 错误码：91019 礼物不存在 / 91020 房间未开播 / 91021 余额不足（**且不产生任何流水**）/ 91022 数量不合法 / 91023 直充金额不合法。

### 5D.2 礼物配置与赠送

- `gift`：名称/图标/单价（金瓜子）/特效类型（1 弹幕区连击 2 全屏特效）/分级（1 普通 2 高级）/上下架。
- **WHEN** 观众赠送礼物（数量 1-999）**AND** 房间直播中 **AND** 余额充足 **THE SYSTEM SHALL** 在单一事务内完成余额扣减、观众金瓜子流水、礼物流水（单价/分成比例按下单时快照）、主播分成流水（比例 700‰，对齐 monetization CHG-02 的 70/30），并在事务提交后向房间 WS 广播 `type=gift` 特效帧（复用 M4-LIV-03 live hub，新增消息类型）。
- **IF** 余额不足 **THEN THE SYSTEM SHALL** 拒绝（91021）且不产生任何流水、不广播。
- 分成流水（`gift_share_log`，uk_gift_log 唯一）为月度结算输入，月度结算归 creator 体系（PAY-02 消费）。

### 5D.3 前端特效（LIV-06 页面挂靠）

- 礼物面板：礼物列表（上架）、金瓜子余额、连击数量、赠送；余额不足提示（开发期引导直充，PAY-01 后换真实充值入口）。
- 特效渲染：普通礼物走弹幕区连击浮层样式；高级礼物全屏 CSS 动画（轻量实现，不引动画库）。

## 5E. 截帧机审与快速切断（LIV-05/§3 边界、§4 合规，V3.3）

### 5E.1 截帧（周期与选型）

- **WHEN** 房间处于直播中 **THE SYSTEM SHALL** 按固定周期（配置 `live.audit.frameIntervalSeconds`，默认 **10s**，对齐 §3 边界的「每 10s」）从 SRS 拉流截取单帧图。
- **截帧源选 HTTP-FLV**（`http://<playDomain>/<app>/room_<id>.flv`），不选 HLS：HLS 是切片式，末片写盘后才有数据，截帧要多等一个目标时长；FLV 是实时转封装，首帧到达即截得到。SRS 5 不提供「截图 HTTP API」（仅有 streams/clients 类 HTTP API 与 http_hooks 事件），故截帧必须由后端调 ffmpeg 完成。
- **调度**：后端进程内定时器 Worker，与 `internal/module/video/transcoder.go` 的 worker 同风格（`time.Ticker` + `ctx.Done()` 退出），**不引入新中间件、不新增独立进程**。
- **开关**：`live.audit.enabled`，**dev 默认 `false`**（避免影响其它测试）；开启后仅对 `status=1` 的房间截帧。
- **IF** 单个房间截帧失败（拉流不通 / ffmpeg 超时 / 进程异常）**THEN THE SYSTEM SHALL** 记录一条 `success=false` 的截帧记录并继续下一个房间，**不得**中断周期调度、**不得**据此切断。

### 5E.2 机审（复用 contentmod；机审不可用时的口径）

- 机审统一走 `pkg/contentmod`（视频机审同款包），**不新起一套审核体系**。
- **能力边界（必须写明的现状）**：`contentmod` 当前公开接口只有 `CheckText`（敏感词 + 规则正则），**图片/外部内容安全 API 是显式 TODO**（包内注释：接入外部图审时增加 external 实现并保持接口不变）。因此本卡在 `contentmod` 增加图片检测入口 `CheckImage`，先落地**无外部依赖的本地画面规则**（低信息量帧：纯色/黑帧/遮挡——这类本身即常见的规避自动审核手段）；外部图审服务保持 TODO 替换点。
- **机审不可用 → fail-open（决策，与项目「Redis 故障放行」口径一致）**：机审链路异常（ffmpeg 不可用 / 截帧图损坏 / 规则执行异常）时 **SHALL NOT 自动切断**，只落一条 `degraded=true` 的截帧记录，直播可用性优先。**该口径是待替换点**：接入外部图审后应改为对「无法判定」与「判定通过」分别计数并按策略收紧（见 plan §2D）。
- 阈值（黑帧亮度上限等）走配置，默认值由 plan §2D 的实测标定给出。

### 5E.3 违规处置与快速切断

- **WHEN** 机审命中违规 **OR** 管理员手动切断 **THE SYSTEM SHALL** 依次：① 落违规流水（`live_violation_log`，含来源 auto/manual、命中原因、切断方式）；② 调 SRS API 踢掉推流（`DELETE /api/v1/clients/<id>`，`<id>` 取自 `GET /api/v1/clients` 中 `publish.active=true` 且流名匹配该房间的客户端）；③ 房间置为封禁（`live_room.ban_status=1` + 原因/操作人/时间）。
- **确定性**：踢流成功后 SRS 触发 `on_unpublish` 回调 → 后端既有 `StopByStream` 把房间置「已下播」（§2.1 状态机 status=2）。封禁是**叠加在状态机之上**的独立标记，不改变 status 枚举语义（不污染既有 `idx_status` 列表查询）。
- **IF** SRS API 不可达 **THEN THE SYSTEM SHALL** 降级为仅改房间封禁状态 + 落违规流水，并在流水中标记 `cut_mode=degraded`（不静默失败；降级事实可查）。
- **IF** 房间未在直播中 **THEN** 手动切断返回可区分错误（91020 语义复用/新增码见 §5E.6），不产生违规流水。

### 5E.4 人工巡查（管理端接口）

- 巡查接口挂后台鉴权链（`AdminAuth` + 权限点 `live:audit`，写法对齐既有 `POST /admin/dev/recharge` 的 `AdminAuth + RequirePerm`）。
- **THE SYSTEM SHALL** 提供三个能力：① 直播中房间列表（含在线人数、最近截帧判定摘要）；② 手动切断（同 §5E.3 处置链，来源记为 `manual`）；③ 恢复（解封 `ban_status=0`，允许主播再次开播）。
- **IF** 请求未携带管理员令牌或令牌无效 **THEN** 401；**IF** 令牌有效但缺少 `live:audit` 权限 **THEN** 403（权限点须落库，非仅路由存在）。

### 5E.5 合规存档

- **THE SYSTEM SHALL** 留存截帧图与判定记录：`live_frame_audit`（每帧一行：房间、图片键、判定结果、是否降级、耗时）+ `live_violation_log`（违规流水）。保留期由配置声明（默认 ≥60 天，对齐 §4）。
- **边界（不在本卡）**：**直播回放视频**存档属 LIV-14（下播转码生成回放稿件）；**推流全量录制**不在第一期。
- **IF** 图片落盘失败 **THEN** 判定记录仍须落库（图片键留空），保证「判定发生过」这一事实可审计。

### 5E.6 错误码

- 沿用 9xxxx 商业化段直播子段（91001-91026 已用），本卡自 **91027** 起：91027 截帧机审未启用 / 91028 房间已被封禁 / 91029 房间未被封禁 / 91030 直播巡查无目标流。
