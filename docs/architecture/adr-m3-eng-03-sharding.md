# ADR：互动明细分表路由（M3-ENG-03）

- **状态**：路由基础已实施，数据迁移待实施
- **日期**：2026-09-13
- **范围**：`comment`、`danmaku`、`user_action`

## 背景

当前三张表均为单表，GORM repository 直接使用模型默认表名。随着评论、弹幕和互动明细增长，单表会带来索引膨胀、热点扫描和归档困难。当前本机可以连接 MySQL，但没有生产量级数据、影子流量或可回滚的双写环境，因此本 ADR 先冻结分片契约，不直接执行破坏性 DDL。

## 决策

采用**应用层逻辑分表**，不使用 MySQL 原生 `PARTITION BY` 作为第一阶段方案：

1. 物理表按固定后缀创建，例如 `comment_00`~`comment_15`、`danmaku_00`~`danmaku_15`、`user_action_00`~`user_action_15`。
2. 分片数第一阶段固定为 16，使用稳定的 `hash64(key) & 15` 路由；禁止运行中随意改变分片数。
3. `comment` 与 `danmaku` 按 `oid/video_id` 路由，保证单个视频的列表查询落在一个分片内；`comment.root_id` 的回复必须继承根评论所在分片。
4. `user_action` 按 `user_id` 路由，保证用户动作去重、收藏夹删除和本人动作查询落在一个分片内。
5. 所有 repository 查询必须通过 `ShardRouter` 生成物理表名，禁止业务代码拼接表名；表名只能来自白名单后缀。
6. 保留逻辑主键 `id`。分片内唯一约束保持原语义；`user_action` 的 `(user_id, oid, obj_type, action)` 在 user_id 分片内继续唯一。
7. 跨分片统计不得依赖单条 SQL 全表扫描，改为按分片并行查询后在应用层聚合；分页使用稳定游标，不能对多个分片做不稳定 offset 分页。

## 现有数据约束

- `comment`、`danmaku` 使用雪花 ID，但现有查询分别按 `oid/root_id`、`video_id/time_ms`，因此不能仅按 ID 哈希拆分，否则单视频列表会跨分片。
- `user_action` 有跨记录唯一语义，按 user_id 分片可以保留去重原子性；按 oid 分片则会让用户动作查询和删除跨分片。
- 评论回复必须与根评论同片；迁移时需要从历史 comment 行解析 root_id，而不能只按当前行 user_id。

## 迁移方案

1. **准备**：新增 `ShardRouter` 纯函数与白名单测试；建立 16 张影子表，结构和索引与单表一致。
2. **双读/回填**：停止写入窗口外先按目标键回填历史数据，校验每个分片行数、主键集合和关键索引查询结果。
3. **双写**：在事务内同时写旧表与目标分片；更新、删除按同一路由键执行，失败时阻断提交并告警。
4. **切读**：按模块逐个切到分片表，保留旧表只读比对窗口；跨分片聚合必须有超时和上限。
5. **收口**：停止旧表写入，完成最终增量回填与校验，保留可恢复备份后再归档旧表。

## 回滚与验收

- 任一阶段可通过 feature flag 切回旧表读写；旧表在收口前必须继续保持完整。
- 验收包括：读写结果一致、重复动作仍被唯一约束拦截、评论楼中楼不跨片、弹幕按视频时间段查询不跨片、跨片统计结果与单表基线一致。
- 本地无生产量级数据和双写环境时，仅允许完成 router/迁移工具/离线校验，不允许将任务标记为生产分表完成。

## 未决事项

- 生产分片数、容量阈值与扩容策略需压测后确定。
- `comment` 的动态对象与视频对象是否共用分片表，需要结合动态流量再定。
- 跨分片热榜/创作者统计需明确缓存与异步聚合方案。
